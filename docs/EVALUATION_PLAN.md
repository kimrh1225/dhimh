# 연구 평가 계획: 일반 ChatGPT vs 구조화된 ChatGPT vs 개발 앱

**성격**: 연구계획서의 핵심 질문을 검증하기 위한 **탐색적 평가 프로토콜**. 수집하지 않은 결과/가상 인터뷰를 실제 증거로 보고하지 않는다.

## 1. 연구 질문

RQ1. 개발 앱은 일반적인 ChatGPT 질의보다 연구 설계상 문제를 정확하고 체계적으로 발견하는가?

RQ2. 개발 앱은 같은 기준을 제공받은 ChatGPT보다 **구조화 입력·피드백 UI·질문·버전 관리** 차원에서 추가 이점이 있는가?

RQ3. 학생은 피드백을 이해·선별하여 본인의 계획을 수정할 수 있는가?

**주의**: RQ2에서 A/B/C 출력 품질만으로 UI/버전 관리의 효과를 인과적으로 주장할 수 없다. 품질 평가와 수정 과업·사용성 관찰을 별도로 수행한다.

## 2. 비교 조건

| 조건 | 실행 방식 | 입력 제한 |
|---|---|---|
| A: 일반 ChatGPT | ChatGPT 새 대화에 표준 계획 전문을 붙여넣고 '이 연구계획의 문제점과 개선 방향을 검토해 주세요.'만 요청 | 후속 대화 없음 |
| B: 구조화된 ChatGPT | 같은 새 대화·동일 계획 전문에 `AI_SPEC.md`의 6개 루브릭과 판단 규칙을 자연어로 제공 | UI·버전 비교 기능 없음 |
| C: 개발 앱 | 같은 계획 내용을 구조화 필드에 입력하고 6개 루브릭 기반 AI 평가 호출 | 앱 고유 구조화 UX 포함 |

**혼란변수 관리**: A/B ChatGPT의 실제 사용 모델은 API 모델과 일치하지 않을 수 있음. 각 조건의 **화면에 표시된 모델명(알 수 없다면 불명으로 기록), 실행 날짜, 설정, 프롬프트 원문, 시행 횟수**를 기록. 완전한 동일 모델·동일 추론 조건을 보장하지 않으면 비교 결과를 '조건별 관찰 차이'로 서술한다. 추가적 통제 연구가 필요하면 동일 API 모델로 A/B/C 프롬프트를 재실행하는 보조 실험을 **별도 표**에 기록한다. 이 보조 실험은 원문의 ChatGPT UI 비교를 대체하지 않는다.

## 3. 표본 준비와 윤리

- 초기 합성 사례(테스트에 한정) 6~10개를 분야·문제 유형별로 작성: 질문 모호, 가설-방법 불일치, 통제 부족, 실행성 불명, 해석 기준 부재, 비실험 연구 등. **이는 성능을 증명하지 않는 예비 케이스**다.
- 실제 학생 참여/계획 사용 시에는 기관 절차, 당사자 동의 및 필요한 보호자 동의, 식별정보 제거, 외부 AI 전송 범위 설명을 선행한다. 대규모 샘플을 확보할 수 없는 8주 제약을 기록한다.
- 외부 LLM 서비스를 사용하는 비교 실험에는 미공개 연구 아이디어 등 민감 정보를 무단 사용하지 않는다.
- 평가자 2인을 섭외할 수 있으면 독립 평가→의견 차이 조정. 섭외할 수 없으면 단일 평가라는 한계를 보고.

## 4. 평가 재료

실험 시작 전 각 연구계획에서 문제 유형에 따른 **기준 이슈 목록(gold issues)**을 평가자 검토로 정의. `case_id`, `domain`, `plan_version`, 이슈 서술, 근거 필드, 심각도, 평가자, 판단 근거를 기록. 생성 결과를 본 후 정답 목록을 편의적으로 변경하지 않는다. 합성 사례에서는 의도적으로 심은 오류와 **그 외 실제 문제 가능성**을 구별하여 평가한다.

## 5. 피드백 평가 기준 및 산식

| 측정 항목 | 실행 방법 | 해석 주의 |
|---|---|---|
| 문제 발견 정밀도(precision) | `TP / (TP + FP)` (해당 결과가 지적한 평가 가능한 이슈) | 근거 없는 지적은 FP; 분모 0이면 N/A |
| 문제 발견 재현율(recall) | `TP / (TP + FN)` (사전 정의한 gold issues) | 정답 목록 불완전성 인정; 분모 0이면 N/A |
| 근거 적합성 | 각 지적과 원문 인용·추론이 맞는지 0~3점 | 정확한 인용이라도 추론이 틀리면 감점 |
| 제안 실행 가능성 | 학생이 실제 수정 행동으로 옮길 수 있는지 0~3점 | 장황함을 품질로 대체하지 않음 |
| 불확실성 표현 | 판단 근거 부족을 인정하는지 0~3점 | 과도한 확언 감점 |
| 사용성/수정 경험 | 계획 수정 과업 수행 여부·이해도/유용성 1~5점·소요시간 | 소규모 관찰, 장기 능력 향상 주장 금지 |

0~3 점수 앵커(공통): 0=부정확/부재, 1=핵심 결함, 2=대체로 적절하나 불완전, 3=명확하고 적절. 각 지표별 평가 문구와 예시를 실험 전에 맞춘다.

**매칭 절차**: 지적(issue) 단위로 출력 분할 → 가명화된 조건 순서로 두 평가자 독립 코딩 → gold issue 연결(TP), 사실과 다르거나 대상 밖의 주장(FP), 누락(FN) → 불일치 조정 후 기록. 같은 이슈 중복 지적을 TP 여러 번으로 계산하지 않는다.

## 6. 블라인딩과 실행 순서

1. 동일 원본 계획을 A/B/C에 입력하며, 한 사례에 대해 연속된 시기에 평가한다.
2. 각 조건은 새로운 대화/비워진 상태로 시작하고, 답변에 재질문하지 않는다(초기 피드백 비교).
3. A/B/C 출력에서 앱·제품명을 제거하고 무작위 ID로 평가자에게 제시. 출력 형식 차이로 완전한 블라인딩이 불가능할 수 있음을 기록.
4. 모델/버전/날짜/프롬프트 길이/총 출력 길이/오류/비용(확인 가능한 경우)을 로그 메타데이터에 기록.
5. 조건별 지표를 사례 단위로 제시(평균·범위와 원자료 표). 표본이 적으면 유의확률 중심 주장 대신 사례별 차이와 한계를 서술.

## 7. 학생 수정 과업(RQ3)

동의를 얻은 소수 참가자에게 자신의 계획 또는 합성 계획을 제공한다. (1) 피드백 검토 (2) 채택할 제안/기각할 제안 표시(간단한 체크 기록) (3) 계획 수정 (4) 무엇을 왜 변경했는지 자유 서술. 평가자는 수정 전/후 계획을 가능하면 익명/무작위 순서로 독립 검토한다. '변경 건수'와 '질 개선'을 동일시하지 않는다. 사용자 경험 점수는 자기보고 지표임을 명시한다.

## 8. 기록 양식

CSV 컬럼(권장):

```text
case_id,condition,run_id,model_label,execution_date,prompt_version,rubric_version,output_length,issue_id,gold_issue_match,tp_fp,source_quote_valid,evidence_score_0_3,actionability_score_0_3,uncertainty_score_0_3,reviewer_id,notes
```

별도 사용자 과업 양식:

```text
participant_pseudonym,case_id,plan_v1_id,plan_v2_id,adopted_issues_count,rejected_issues_count,task_completed,task_minutes,clarity_1_5,usefulness_1_5,change_rationale,consent_record_id
```

자료는 연구 수집 범위와 저장 기한을 사전에 정해 보호하고, 앱은 이를 자동 업로드/수집하지 않는다. 수집 전 체크리스트를 확인하고 실험 날짜·모델 명세·실제 표본 수를 결과 장에 기입한다.

## 9. 보고할 한계

- 가상 인터뷰는 실증적인 요구 조사 결과가 아니다.
- ChatGPT UI 모델과 API 모델/시스템 프롬프트를 동일하게 통제하기 어려움.
- 분야별 전문성 한계, 작은 표본, 평가자 편차, 순서 효과, 학습 효과.
- 피드백의 품질과 학생의 **장기적인 연구 능력 향상**은 별개.
